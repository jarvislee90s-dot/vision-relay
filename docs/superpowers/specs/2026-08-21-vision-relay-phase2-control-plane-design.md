## 1. 背景与动机

一期交付了数据面（8787 三协议代理、图片管线、fail-open）与最小 CLI。实际使用暴露三类问题：

1. **配置体验差**：模型看图能力的确认是终端问答（TUI），VLM 配置靠手改 JSON——门槛高、易错、不可视。
2. **接线是一锤子买卖**：harness 的 base_url 只在服务启停时改写。运行期间 CC Switch / Codex++ 开关路由、用户换供应商、手动编辑配置，代理都不感知——安全网被静默绕过。更糟的是服务异常中断后 base_url 残留指向死端口，**所有 harness 直接瘫痪，比没有安全网更糟**。
3. **安装分发是两件套**：Python 环境 + pip 安装对普通用户不可用。

同期确认的长期方向：**多 harness 信息拦截 / 提示词注入 / 统一调度平台长在 Python 核心里生长**（一期 IR 层是现成的插槽），GUI 永远只是管理壳。因此二期把投资集中在控制面，并留好插槽、不实现平台功能。

## 3. 术语与全局决策

- **模态表述统一为「图片 / image」**：能力值、UI 开关、文档措辞统一用「支持图片 / 纯文本」，消除「视觉」与 video 的歧义（模型模态 = 文本 / 图片 / 视频 / 语音）。配置层新值 `image`，旧值 `vision` 读兼容（不破坏现有 proxy.json）。泛化概念（「视觉安全网」、项目名 vision-relay、VLM = 视觉语言模型的通用叫法）保留。
- **自动决策框架（二期 GUI 的骨架）**：每个面向用户的交互过三问——能从已记录状态/规则推导 → 系统自动做、零感知；推导不出但有安全默认 → 默认自动 + 被动通知可改；需要用户资源或真实意图 → 才暴露。配套铁律「自动化之后可见性补位」：每个自动动作在总览与事件日志留痕。**用户决策点收敛为 6 个**（路由总开关、首次填 VLM、首次过目模型能力、缺 key 补填、关闭 GUI 选择、稀有停用转发）。
- **平台方向**：拦截 / 注入 / 调度逻辑未来长在 Python 核心（IR 层 transformer 链插槽），三期另立 spec；GUI 永远是薄壳、可整体替换。
- **接线规则 = 始终接管**：服务运行期间，harness 的 base_url 一律指向本代理；路由工具的开关只决定本代理往哪转发（工具在线 = 两层经工具；离线 = 一层直连回落）。
- **幽灵控制面结案**：一期设计的 8788 控制 API 从未实现；本期以「不需要它」结案——GUI 通过核心 CLI 的 JSON 问答通信，`ui_port` 从配置与输出中移除，不新增第二个监听端口。
- **旧 spec 移交**：旧二期路线图加注记——Web UI 章节被本 spec 取代（方向从自包含网页改为 Tauri 桌面应用）；数据面项移三期。

**从需求推导出的架构规则：**

- R1–R8 全是管理面需求 → 管理逻辑全部长在 Python 核心（沿用一期已验证代码与测试体系），GUI 只是操作台。由此两条硬规则：**① GUI 与核心之间用稳定的、带版本号的 JSON 问答契约；② GUI 不自己解析任何配置文件**（哪怕只读展示也问核心，防止解析逻辑双语言漂移）。
- R2/R3/R4 本质是同一个问题——「实际接线状态」与「应有状态」不一致 → 核心里做**统一的对账引擎**，所有触发源（GUI 刷新按钮、自动监听、启停、诊断修复）走同一套规则。
- R7 要求单包 → 核心用冻结打包（含运行时的自包含程序）随 GUI 安装包分发，GUI 负责拉起/停止核心进程；GUI 与核心同包同版本。
- 一期数据面（协议归一化、图片管线、fail-open 不变量）**不动**；唯一的数据面增量是识图留痕（R6）。

**多写者现实与对策**（harness 配置文件有四个可能的写者：本代理、路由工具、供应商切换、用户手编。前三个争的都只有 base_url 一个字段，第四个偶尔整文件手改）：

- 严格的「排队」做不到（外部进程不受我们约束）→ 采用**期望状态 + 对账**模式（控制器思路）：
  1. **原子写**：所有写操作先写临时文件再一步替换，读者永远看不到半成品（一期已具备）；
  2. **自方排队**：本代理自己的写者（GUI 触发的动词、后台对账）之间用文件锁排队；
  3. **变更监听**：用操作系统文件通知（参考 CC Switch 的做法：事件通知 + 防抖 + 快照比对防自触发；Codex++ 的做法：每请求重读配置）感知外部改动，监听目标收窄为三个 harness 文件的 base_url 字段 + 本代理自身配置；
  4. **幂等对账**：实际 ≠ 期望就收敛，无漂移不碰文件。

## 5. 对账机制与接线规则

**期望状态**

- 服务运行中：每个启用的 harness，base_url 一律指向本代理（始终接管）；转发方向看工具：工具端口在线 → relay 指向工具（两层）；离线 → 一层直连回落，无可用直连 relay 时 GUI 明确警告「该 harness 当前无上游可用」。
- 服务停止：harness 恢复原状（按接管组合快照），自动添加的 relay 一并撤销。
- qwen-code 无路由工具，永远一层直连。

**观测信号（三个）**

1. 三个 harness 配置的 base_url 当前归属（本代理 / 已知工具端口 / 陌生地址）；
2. 已知路由工具的端口在不在线——只探端口通断，不做内容指纹（沿用一期「抗干扰」约束）；
3. 服务自身健康（进程存活 + 端口监听双信号，僵死 PID 自动清理）。

**对账规则矩阵**（唯一逻辑，所有触发源共用）

| 实际情况 | 处理 |
|---|---|
| 服务在跑，接线正确，relay 与工具状态一致 | 不动任何文件（幂等） |
| 服务在跑，harness 被工具改指工具端口 | 抢回：base_url → 本代理，relay 确认指向该工具；记录事件 |
| 服务在跑，工具路由关（端口离线） | base_url 保持本代理；relay 回落直连；无直连 relay 则警告 |
| 服务在跑，harness 被改成陌生地址（用户换供应商） | **吸收**：接管回本代理，同时把新地址记为该 harness 的直连上游；GUI 明确告知「检测到上游变为 X，已接管、转发已指向 X」，缺 key 则提醒补 |
| 服务已死，harness 仍指向本代理 | 进入修复流程 |
| harness 配置出现新模型 | 不碰 base_url；GUI 提醒批量确认图片能力 |

**备份、快照与回退语义**

- **接管组合快照**：每次接管（含对账吸收新上游）时，把该 harness 的 **base_url + API key 所在位置 + 模型名** 作为一组快照记档（每 harness 只存最新一条，不做历史清单）。动机：CC Switch 直连切换模式会把 live 文件回读进它自己的供应商档案——本代理写入的 8787 可能被它读走，造成其档案内「8787 + 别家 key/模型」的错位污染；本代理不写工具的库（只读硬约束），但凭快照始终持有「正确组合」的真相，任何还原都按组合写回，不受污染备份影响。
- **备份**只记「本代理第一次接管之前的原始值」，之后反复抢线不覆盖（防止备份被污染成本代理地址）；恢复即回到那个原始状态。
- 每次抢回 / 修复 / 吸收 / 自动标注事件进事件日志（何时、哪个 harness、从什么改成什么），GUI 可查。

**修复流程（R3，按自动决策框架定稿）**

先查服务状态；服务已死且接线仍指向本代理 = 事故。**修复全自动，按崩溃前意图推导目标**：

- 漂移抢回（服务运行中 base_url ≠ 本代理）、僵死 PID 清理：确定性动作，直接执行并留痕；
- 僵尸接线：**崩溃前路由开关是开的 → 自动重启服务并保持接管**（最忠实还原用户意图）；**是关的 → 按接管组合快照还原**（组合内容在诊断报告中可见）；
- 缺 API key：系统无法代填（账号资源），被动提示补填——这是「需要你」区唯一常住项；
- **只有无解项才出现选择**：快照读不到 且 服务起不来时，诊断报告才给出手选/手输入口（动手前展示将恢复到什么）。

诊断报告因此是**只读报告**而非操作台：能自动修的已直接修并记录在案，用户看的是结果与依据。配套「直连连通性测试」诊断项（自动运行）：路由关闭（直连态）时，用各 harness 自己配置的 base_url + key 做轻量探测，帮助区分「问题本来就有」还是「本代理造成」。所有修复项提供「打开配置文件对应位置」快捷入口。

**路由工具档案（R4，一期 §12 清单的升级）**

每个已知工具一条档案：名字 + 默认端口 + **支持的 harness 矩阵** + 生成的 relay 模板 + **激活供应商读取方式**。注意 CC Switch 同时覆盖 Claude Code 与 Codex——某 harness 的第二跳归属（CC Switch 还是 Codex++）**以接管快照记录为准**，快照缺失时端口探测兜底，仍不明确则 GUI 询问一次并记住。真实上游的解析优先级：

1. 一层直连：relay 的 base_url 即答案（本代理配置，必然可得）；
2. 两层经工具：读工具自身的配置获得当前激活供应商及其 base_url（Codex++ 读其 settings.json；CC Switch 读其配置库，读不到退而调其端口上的状态接口）；
3. 都失败：诚实显示「由某工具决定（未知）」——不猜。

显示规则：**优先显示 base_url（端点），拿不到才退到供应商名 / 模型名**。工具探测全部只读，绝不写工具的配置。清单可扩展（TRAE / Kimi 等未来加条目即接入）。

**监听分阶段**：先手动刷新（GUI 按钮 + CLI 动词，本期必交付）；后自动监听（服务内文件通知 + 周期对账，可开关、默认开）。

**模型能力标注（R9：三元组键 + 四级依据 + 可验证探针）**

- **唯一键 = (harness, provider, 模型) 三元组**：同一模型名经不同 provider 能力可能不同（如 Claude Code 同时配两家供应商）。provider 自动填充——两层拓扑 = 路由工具当前激活供应商（工具档案只读）；一层直连 = 接管快照 / relay 的上游。用户不用手填。旧配置的按组扁平存储读兼容迁移。
- **判定优先级：用户覆盖 > 实测探测 > 能力目录 > 未知默认纯文本**。
- **可验证探针（实测探测）**：对每个 (provider, 模型) 用已配 key 发一次最小带图请求——图里藏一个字，问「图里是什么」。三档判定：**报错**（明确拒绝图片输入）→ 纯文本；**答对**（真读到图）→ 支持图片；**返回 200 但答错**（静默吞图，真实存在的坑）→ 纯文本。超时 / 401 / 404 / 5xx 不下结论，回落目录。成本为每模型一次最小调用，结果按 (provider, 模型) 缓存、可重测；没配 key 的 provider 显示「未测」按目录标注。
- **能力目录**：models.dev 风格静态目录（provider+model → 输入模态 / 上下文长度 / 推理档位），作为离线兜底（探测不可用或未测时）；可选「从上游拉取模型清单」（用已配 key 调 `/v1/models`，只补模型 ID 清单，能力元数据以探针与目录为准）。
- **误标的双向代价写进 UI 文案**：视觉模型标成纯文本 → 每张图都经 VLM 转述（费 token + 降质）；纯文本标成视觉 → 请求报错——这是首次向导保留「过目」步骤的原因（实测结果已就绪，用户只改猜错的）。
- 视频 / 音频模态探测同思路，留三期（本期只做 image）。

## 6. GUI 设计（Tauri + React，导航 5 页 + 触发型首次向导）

交互布局参考（定稿线框，浏览器直接打开、顶部标签仅为文档目录、页内可交互：路由开关/工具圆点/详情抽屉/诊断报告）：[gui-mockups/index.html](gui-mockups/index.html)。

信息架构原则（定稿）：**看编分离**——监控类页面只看 + 少数动作，编辑集中在「设置」与「模型能力」；识图记录、事件日志是纯看板（看不需要决策，保留可视化）。**保存语义统一**：输入类控件（含开关、勾选）一律经所在页底部统一「保存」生效并带未保存指示；只有按钮类动作（刷新、诊断、路由开关）即时生效。**自动决策框架**见 §3（用户决策点 6 个）。

| 总览 | R2/R8 | ① 状态横幅：**滑动式路由开关**（启停服务+接线）、刷新（便捷动作，自动对账默认在跑）、**诊断报告**（只读；角标 = 未解决问题数，修复完成才减少）。② 三个 harness 拓扑卡：**竖排链路、动态渲染**——路由关则本代理节点置灰「已旁路」、连线右移直连下一跳；工具也关则再右移直连真实上游；卡上显示激活供应商及其 base_url（§5 优先级）。③ 卡片「详情」抽屉（默认折叠）：接管组合快照、本 harness 的 relay（来源/匹配模型/停用转发）、配置文件路径与行——转发与工具看板并入此处，不设独立区块。④ **「自动处理」区**（被动通知：自动抢回、自动修复、新模型已实测标注、连通性自动测试——全是绿条只读，点开看事件）；**「需要你」区**（仅缺 key 补填一类）。⑤ **诊断报告弹层**（只读）：能自动修的已直接修并记录；仅无解项（快照读不到且服务起不来）才出现选择。漂移由对账自动收敛，**不设手动抢回按钮** |
| 模型能力 | R1/R9 | **三元组表格**（harness × provider × 模型，provider 自动填充）+ 当前标注 + 依据（实测/目录）+ **实测列**（报错=纯文本 / 答对=支持图片 / 吞图=纯文本 / 未测）+ 操作（切换、重测）；「探测全部未测模型」与「从上游拉取模型清单（可选）」按钮；**查看与覆盖**定位——进来就是标注完的表，只在猜错时改，一次保存生效 |
| 识图记录 | R6 | 一级按 harness、二级按会话（标识来自请求元数据，尽力而为；**会话短名**读 harness 会话目录，读不到显示截断 ID，不硬造；无标识归「未识别会话」）；单次明细：缩略图 + 哈希、①提示词（标注当前生效的是默认还是自定义）→ ②VLM 原始返回 → ③实际注入文本（如实显示预算截断）；留存与导出（策略在设置折叠区） |
| 事件日志 | R2/R3 | 自动动作全程留痕（自动化之后可见性补位）：抢回 / 吸收 / 接管 / 自动修复 / 自动标注 / 异常退出，何时、从什么改成什么；筛选与导出 |
| 设置 | R1/R5 + 全局配置 | **VLM**（唯一必配卡：模型名称 / base URL / API key 带表头 + 保存 + 可选测试）→ **按 harness 分组状态表**（跟随全局 ✓ / 自定义，点开才展开自定义四件套，默认零配置）；**外观**（语言：跟随系统/中文/English，可见）；**折叠区·识图提示词**（Tier1/Tier2 可编辑保存、一键恢复默认；测试四模式：Tier1×默认/自选、Tier2×默认/自选，走生产调用路径）；**折叠区·服务与高级**（全部默认值：监听 127.0.0.1:8787、管理的 harness 自动检测已安装者、自动对账开·5 秒、识图留痕 7 天·仅本机、版本与契约）。relay 管理（停用/补 key）在总览详情抽屉，GUI 不提供手工新建 relay（§5） |

**首次运行向导**（触发型弹层，不在导航；触发 = proxy.json 不存在，或存在但首次确认标志未置位；升级与新模型不重跑，走模型能力页增量）：两步——① 配置 VLM（账号资源，必填）→ ② **过目模型能力**（探测已自动跑完，三元组表 + 实测结果，只改猜错的，**可跳过**=按目录/默认）→ 完成才允许开启路由。原终端向导保留（无 GUI 场景）。

**生命周期语义（R8）**：路由开关 = 启停服务 + 接线/还原；GUI 关闭弹确认（「仅关闭界面，服务继续」/「关闭界面并停止服务」，可记住选择）；系统托盘纯文字菜单：状态行（运行中 · 端口）· 打开主界面 · 路由：开/关 · 诊断报告 · 退出（停止服务）。

## 7. 配置与数据变更

1. **VLM 按 harness 分组**：新增按 harness 的 VLM 配置组；现有全局段降为默认兜底，未配置的组回落全局。
2. **能力值术语与存储**：新值 `image`，旧值 `vision` 读兼容；能力记录按 (harness, provider, 模型) 三元组存储（旧按组扁平结构读兼容迁移）；内置供应商名单升级为**能力目录**（models.dev 风格，provider+model → 模态/上下文/推理档位）；**探针结果按 (provider, 模型) 缓存**、可重测、随判定优先级参与标注（§5）。
3. **接管组合快照与备份**：见 §5（每 harness 只存最新组合，不做历史清单；用户自定义回退档案已由「按崩溃前意图自动推导」取代，若仍有需求留三期）。
4. **识图提示词可自定义**：Tier1/Tier2 默认提示词可在 GUI 编辑、保存、一键恢复默认；识图管线读取当前生效值；测试面板支持默认/自选提示词 × Tier1/Tier2 四种组合。
5. **relay 压制名单**：用户停用自动探测生成的 relay = 显式意图，记入压制名单，自动探测不再加回。
6. **识图留痕**：本地留存（默认 7 天、可关闭）；记录含提示词与原始返回，属敏感数据，只存本机、不随任何上报外发。
7. **移除 `ui_port`**：配置、CLI 输出、check 全部清理（含一期 spec 中相应表述的勘误注记）。

## 8. 分发与安装（R7）

- **单一安装包**：GUI + 冻结核心同包（Windows MSI/EXE、macOS DMG 拖拽安装、Linux AppImage/deb），安装即用、零 Python 依赖；GUI 管理核心进程的拉起与停止。
- **一个版本号**：同包同版本发布；JSON 契约带版本字段，兼容「用户单独升级了 pip 版核心」的残余场景（GUI 检测到不匹配给升级指引，不莫名报错）。
- **pip 通道保留**：高级用户 / 无界面场景（CI、服务器）仍可 `pip install vision-relay` 纯 CLI 使用。
- 已知代价（记档，不阻断）：安装包约 50–80MB；冻结程序偶发杀毒软件误报（缓解手段在实现计划中评估）；暂不做签名 / 公证。

## 9. 风险与优先级

| 级别 | 事项 | 说明与要求 |
|---|---|---|
| **P0** | 配置双写冲突 | GUI 与常驻服务同时改同一批文件会互相覆盖丢改动。要求：自方写者全局排队（文件锁）+ 原子写 + 每次改动留痕 |
| **P0** | 僵尸接线 | 服务异常中断后 harness 指向死端口，全部 harness 瘫痪。要求：任何时候可检测、自动修复（按崩溃前意图），修复动作与目标可观测 |
| **P0** | 单包分发 | 硬约束（R7），决定技术路径（冻结打包 + sidecar） |
| **P0** | 对账引擎 | 所有接线变更的唯一通道，规则矩阵见 §5 |
| **P1** | 外部变更监听 | 文件通知 + 防抖；只盯 base_url 与本代理配置；幂等对账 |
| **P1** | 外部工具档案污染 | CC Switch 直连切换会把 live 文件回读进其供应商档案，本代理写入的 8787 可能被存成「8787 + 别家 key/模型」的错位组合。对策：接管组合快照（§5）保住正确组合的真相；绝不写工具的库 |
| **P1** | 模态探测误判/成本 | 静默吞图（200 但没读图）会误判支持图片——可验证探针（图里藏字问答案）专防此坑；探测含糊（超时/401/404/5xx）不下结论回落目录；成本 = 每模型一次最小调用并按 (provider, 模型) 缓存，不重复花 |
| **P1** | 抢线窗口 | 工具改写 base_url 到本代理发现之间的短窗口图片可能漏过。接受窗口存在；每次纠正留事件日志；无漂移不写文件 |
| **P1** | GUI/服务生命周期 | 显式开关、关闭确认、托盘（R8） |
| **P1** | 新模型提醒 | 批量确认入口 |
| **P1** | 契约版本 | 防 GUI 与核心版本脱节 |
| **P2（下期/按需）** | 签名 / 公证、安装包体积优化、状态推送流 | — |

## 10. 测试与验收

- **Python 核心**：管理动词单元测试；对账规则矩阵测试（模拟四类漂移：被工具改走 / 工具离线 / 陌生地址吸收 / 僵尸接线自动修复——按崩溃前意图推导目标）；模态探针三档判定测试（报错 / 答对 / 吞图 / 含糊不下结论）与缓存；能力目录查询；识图留痕与留存清理；锁与原子写。
- **契约测试**：全部 `--json` 输出的结构稳定性（GUI 与核心不脱节的护栏）。
- **GUI**：三平台手工测试手册（沿用一期 manual-test 惯例）；打包冒烟（安装 → 起服务 → 开关路由 → 诊断报告）。
- **端到端验收剧本**：
  1. 开启 / 关闭路由（开关、接线、还原全程正确）；
  2. 强杀服务进程 → 诊断报告呈现僵尸接线 → **自动修复**（崩溃前路由开 → 重启保持接管；关 → 按快照组合还原），修复动作全程留痕可见；
  3. CC Switch / Codex++ 运行期开关路由 → 自动抢回 / 回落直连，事件留痕；
  4. 换供应商（base_url 变陌生地址）→ 自动吸收为新直连上游 + 新模型自动探测标注（实测列可见）+ 被动通知；
  5. 按 harness 配置不同 VLM 并各自测试通过（分组默认跟随全局）；
  6. 识图记录按 harness → 会话归档，三段内容（提示词 / 原始返回 / 注入文本）可查；
  7. 关闭 GUI（选「仅关界面」）服务存活，托盘文字菜单可启停路由；
  8. 首次向导两步走完（填 VLM → 过目实测标注，可跳过）→ 开启路由即受保护。

## 12. 明确不做（本期范围外 → 三期）

- 多 harness 拦截 / 注入 / 调度平台（IR 层 transformer 链——本 spec 只留插槽方向：注入类变换未来挂在 IR 层，不另开解析路径）；
- 新 harness 接入（OpenCode、DSH、TRAE、Kimi）、DSH 准入声明；
- 磁盘缓存、后台深缓存、跨协议流式（Responses ↔ 其他）、Claude Code hooks、上游转发重试、请求级总超时；
- relay 多供应商轮转、服务端部署、签名 / 公证。

## 13. 决策记录（2026-08-21 与用户逐条确认）

| 决策点 | 结论 |
|---|---|
| 二期范围 | 聚焦控制面（GUI + 对账 + 修复 + 自动探测 + 打包）；数据面增强全部移三期 |
| GUI 技术栈 | Tauri + React（UI 质量与生态优先；两参考项目同栈；GUI 是薄壳、可整体替换） |
| 平台方向 | Python 核心生长；GUI 永远是管理壳；未来平台功能长在核心 IR 层 |
| GUI↔核心通信 | 核心管理动词 `--json` 子进程契约；不实现 8788 控制 API；移除 `ui_port` |
| 代码布局 | 同仓库 monorepo（`gui/` 目录）；GUI 与核心同版本发布 |
| 接线规则 | 始终接管（服务运行期间 base_url 一律指向本代理；工具开关只决定 relay 指向） |
| 多写者机制 | 期望状态 + 对账（原子写 / 自方文件锁 / 文件通知监听 / 幂等收敛），不做跨进程排队 |
| 修复语义 | 全自动：漂移抢回 / 僵死 PID 直接执行；僵尸接线按崩溃前意图推导（路由开 → 重启保持接管；关 → 按快照组合还原）；缺 key 被动提示；仅「快照读不到且服务起不来」才出现手选入口 |
| 接管组合快照 | 接管时记 base_url + key 位置 + 模型的组合，防外部工具档案污染造成的错位；第二跳归属（CC Switch 也可能路由 Codex）以快照为准、探测兜底 |
| 真实上游显示 | 直连 = relay base_url；两层 = 读工具激活供应商（Codex++ settings.json / CC Switch 配置库 / 状态接口）；都失败诚实显示未知；优先显示 base_url |
| VLM 分组 | 按 harness（入站协议判组）+ 全局兜底 |
| 识图记录 | 一级 harness / 二级会话（尽力识别，短名读 harness 会话目录、读不到显示截断 ID）；三段明细；本地留存 7 天可关闭 |
| 识图提示词 | Tier1/Tier2 默认提示词可在 GUI 自定义、保存、一键恢复默认；测试支持默认/自选 × Tier1/Tier2 四种模式 |
| 自动决策框架 | 能推导→自动；有安全默认→默认+被动可改；需资源/意图→才问；自动动作全留痕（可见性补位）。用户决策点收敛为 6 个：路由总开关 / 首次填 VLM / 首次过目模型能力 / 缺 key 补填 / 关 GUI 选择 / 稀有停用转发 |
| GUI 信息架构 | 导航 5 页（总览 / 模型能力 / 识图记录 / 事件日志 / 设置）+ 两步首次向导；看编分离、看板保留（看不需要决策）；总览分「自动处理」被动区与「需要你」区；诊断报告只读（自动修复直接执行并留痕，仅无解项才出现选择）；转发与工具看板并入 harness 卡详情抽屉；拓扑链动态渲染（旁路节点置灰、连线右移）；不设手动抢回按钮 |
| 模型能力键 | (harness, provider, 模型) 三元组；provider 自动来自工具档案/接管快照；判定优先级：用户覆盖 > 实测探测 > 能力目录 > 未知默认纯文本 |
| 模态探测 | 可验证探针（图里藏字问答案）：报错=纯文本、答对=支持图片、吞图(200 答错)=纯文本；含糊不下结论回落目录；每模型一次最小调用、按 (provider, 模型) 缓存可重测；`/v1/models` 仅用于拉模型清单 |
| 能力目录 | models.dev 风格静态目录（provider+model → 模态/上下文/推理档位）作离线兜底；内置供应商名单升级而来；视频/音频探测留三期 |
| relay 的 GUI 边界 | GUI 不提供手工新建 relay：来源仅自动探测 + 快照吸收，界面只读 + 停用转发 + 补 key；自定义转发规则的高级用户直改 proxy.json（文档说明） |
| 保存语义 | 输入类控件一律页底统一保存（未保存有指示）；仅按钮类动作（刷新/诊断/路由开关）即时生效；语言选择（跟随系统/中文/English）保持可见 |
| 模态术语 | 统一「图片 / image」；配置值 `image`（读兼容 `vision`）；泛化概念保留 |
| 分发 | 单一安装包（冻结核心随包）；pip 保留为高级通道 |
| GUI 生命周期 | 显式路由开关 + 关闭确认二选一（可记住）；托盘纯文字菜单：状态行 / 打开主界面 / 路由开关 / 诊断报告 / 退出停止服务 |
